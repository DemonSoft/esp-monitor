# Руководство по визуализации и мониторингу метрик ESP8266 / ESP32

Настоящий документ содержит практические рекомендации, PromQL-запросы и шаблоны для настройки Grafana при работе с метриками состояния пинов микроконтроллеров, собираемыми через связку Vector и VictoriaMetrics.

---

## 1. Прокачка Grafana & PromQL

Благодаря tag-based (label-based) архитектуре, где имя метрики едино (esp_pin_value), а метаданные распределены по тегам device_id (идентификатор платы) и pin (имя пина), в Grafana можно строить динамические и гибкие аналитические панели вместо сотен однотипных графиков.

### Базовые PromQL-запросы

* Вывод конкретного пина для определенного устройства:
  esp_pin_value{device_id="esp32_kitchen", pin="GPIO12"}

* Агрегация данных (например, среднее значение аналогового пина по всем устройствам):
  avg by (pin) (esp_pin_value{pin="A0"})

### Динамические дашборды с переменными (Variables)

Чтобы не создавать отдельный график под каждый пин или устройство, используйте механизм переменных Grafana. При выборе устройства в выпадающем списке список пинов будет адаптироваться автоматически.

1. Создание переменной для устройств ($device):
   * Тип: Query
   * Имя (Name): device
   * Data Source: Ваш VictoriaMetrics/Prometheus
   * Запрос (Query): label_values(esp_pin_value, device_id)
   * Multi-value / Include All: По желанию.

2. Создание зависимой переменной для пинов ($pin):
   * Тип: Query
   * Имя (Name): pin
   * Data Source: Ваш VictoriaMetrics/Prometheus
   * Запрос (Query): label_values(esp_pin_value{device_id="$device"}, pin)

3. Универсальный запрос для панели (Panel Query):
   * Использовать в градиентах или State Timeline:
     esp_pin_value{device_id="$device", pin="$pin"}

### Аналитика изменений (Rate / Changes)

Для цифровых пинов (0 или 1), к которым подключены реле, кнопки или датчики движения (PIR), часто важно знать не просто текущее состояние, а интенсивность событий.

* Подсчет количества переключений (срабатываний) датчика/реле за последний час:
  changes(esp_pin_value{device_id="$device", pin="$pin"}[1h])
  
  (Полезно для построения тепловых карт (Heatmaps) или Bar charts, отображающих активность датчиков в разное время суток).

## 2. Мониторинг работоспособности устройств (Heartbeat / Watchdog)

В потоковой IoT-архитектуре, если микроконтроллер зависнет, отключится от Wi-Fi или потеряет питание, он просто перестанет отправлять сообщения в Kafka. VictoriaMetrics не получает новых точек данных, а Grafana по умолчанию продолжит отображать последнее известное состояние (или пустоту, в зависимости от настроек панели).

Для своевременного обнаружения "отвала" устройств (Dead Node Detection) применяются следующие подходы в PromQL.

### Способ 1. Использование функции absent()

Функция возвращает 1, если метрика полностью отсутствует в базе данных за последнее время.

* Проверка доступности конкретного устройства:
  absent(esp_pin_value{device_id="esp32_kitchen"}) == 1
  
  (Недостаток: неудобно масштабировать на сотни динамических устройств).

### Способ 2. Сравнение временных меток (Рекомендуемый универсальный вариант)

Более гибкий подход — вычисление разницы между текущим временем сервера и временем последней записанной точки для каждого устройства.

* Выявление устройств, не присылавших данные более 2 минут (120 секунд):
  time() - max by (device_id) (timestamp(esp_pin_value)) > 120

### Настройка Alerting в Grafana

На основе верхнего запроса можно создать правило оповещения (Alert Rule):

1. Expression: time() - max by (device_id) (timestamp(esp_pin_value)) > 120
2. Условие (Condition): Если выражение истинно (возвращает значения), значит, есть «молчащие» устройства.
3. Аннотации (Annotations):
   * Summary: Устройство {{ $labels.device_id }} недоступно!
   * Description: Плата {{ $labels.device_id }} не отправляла метрики состояния пинов в Kafka уже более 2 минут. Проверьте питание или подключение к Wi-Fi.
4. Каналы уведомлений: Telegram, Slack, Email или Discord через Grafana Alertmanager.
