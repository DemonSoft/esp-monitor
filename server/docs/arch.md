# Архитектура.
# ===============

## Назначение:
---------------
Текущий сервис предназначен для удаленного управления конфигурациями предустановленных микроконтроллеров серии ESP / Arduino.

## Основные функции:
------------------
01. Загрузка списка предустановеленных микроконтролеров в виде .cvs файла.
02. Обновление списка (добавление новых микроконтроллеров, обновление информации об уже добавленных).
03. Отображение списка состояний загруженных микроконтроллеров в табличном виде в браузере.
04. Активация микроконтроллера из списка путем подключение к нему при помощи клиентского приложение.
05. Добавление микроконтроллера из клиентского приложения.
06. Мониторинг текущего состояния посредством брокера MQTT.
07. Передача обновленной конфигурации на микроконтроллер посредством брокера MQTT.
08. Минимальная админ-панель на web.
09. Удаление микроконтроллера.
10. Запись событий в Kafka.


## Дерево проекта:
----------------
1. *server* - содержит метод main исполняемого файла сервиса.
2. *docs* - текстовые файлы, с описанием хода работы над проектом, пользовательскую и проектную документацию.
3. *internal* - содержит исходный код сервиса, разбитый на подкатегории.
    - *database* - пакеты работы с базой данных.
      -- *sqlite* - пакет встроенной БД sqlite
        --- *shemes* - папка с файлами миграции sqlite
      -- *postgres* - пакет заглушек для postgresql
    - *domain* - пакеты бизнес-логики.
      -- *env* - пакет создания кофигураций и окружения.
      -- *ulils* - пакет с полезными функциями, не привязанными к бизнес-логике.
    - *model* - пакеты типов данных.
    - *network* - группа папок сетевых провайдеров.
      -- *rest* -  сетевые запросы REST
      -- *mqqttserice* - сетевые MQTT запросы.
      -- *kafka* - сетевые запросы к kafka
      -- *web* - шаблоны веб-страниц и другие веб-ресурсы.
4. *test* - группа содержит ресурсы для тестирования.
  - csv - примеры .csv файлов, которые используются для отработки сетевых запросов с передачей данных.

 -----------------------
 Переменные окружения задаются в .env файле. Само собой, этот файл находится в списке .gitignore. Если планируется использовать постоянные значения для переменных оурежения, то его можно создать при помощи скрипта:

 DB_NAME=<DATABASE NAME>

## Command-line
---------------
xToken -  параметр command line, который передается в заголовках (headers) REST запроса со стороны клиента. Если значение xToken не совпадает, то запрос отклоняется на этапе middleware. Если xToken не задан в виде command line, то это значение будет прочитано в .env файле.
Пример:
server -xToken <YOUR SECRET STRING OR UUID, GUID AND OTHERS>

## Подерживаемое Rest API
---------------
По-умолчанию, сервер запускается на 80-м порту.
Порт можно переопределить следующим образом:
- в файле .env переменной REST_PORT: REST_PORT=80
- в методе CreateCfg пакета Rest.
- в методе main (): cfg := rest.Config{Port: <CUSTOM PORT>}
Рекомендуется использовать переменную REST_PORT, поскольку, это позволяет развертывать сервер в контейнере Docker  в автоматическом режиме.

**HTML**
* / - Возвращает дефолтную веб-страницу.
* /devices - краткая информация обо всех устройствах (SSDP name, статус активности, аптайм).
* /devices?token=<YOUR XTOKEN> - расширенная информация обо всех устройствах.
* /devices/info?token=<YOUR XTOKEN>&ssdp=<DEVICE SSDP> - информация о конкретном устройстве, включая последний переданный action.
* /devices/cfg?token=<YOUR XTOKEN>&ssdp=<DEVICE SSDP> - форма для задания конфигурации устройства.

**JSON**
GET /api/v1/devices - список всех зарегистрированных устройств.
GET /api/v1/devices?filter=esp-001 - список устройств, начинающихся с *esp-001*.
POST /api/v1/cfg
  - поле хедера SSDP содержит ssdp name устройства, для которого передается новая конфигурация.
POST /api/v1/upload. 
  - поле body содержит .csv файл
DELETE /api/v1/devices
  - удаляет устройство, заданное в поле ssdp.

## CURL
-----------
В случае, когда необходимо осуществить запрос без использования клиентского приложения, но, запрос требует наличия xToken или других пермишенов, можно воспользоваться стандартной утилитой curl, чтоб выполнить запрос из терминала.
*Примеры:*
curl -# -X POST 127.0.0.1/api/v1/devices/upload -H "xToken: <XTOKEN>" -F "body=@./tests/csv/devices.csv"
curl -X GET 127.0.0.1/api/v1/devices -H "xToken: <XTOKEN>"
curl -X GET '127.0.0.1/api/v1/devices?filter=esp-002' -H "xToken: <XTOKEN>"
curl --get '127.0.0.1/api/v1/devices' -H "xToken: <XTOKEN>" -d "filter=esp-002"
curl --get  '127.0.0.1/devices' -d
curl --get  '127.0.0.1/devices' -d "filter=esp-002"

## REST Response
----------------
Если запрос успещен, то  сервер возвращает HTTP CODE 200 и объект следущего вида:
{
    "data": <ARRAY, DICTIONARY OR JSON TYPE>,
    "error": null
}
В поле "data" может содержаться произвольный допустимый JSON тип. Конкретная форма зависит от запроса.
Поле "error" явным образом возвращает значение null.
Если при выполнении запроса возникла ошибка, к примеру, не был задан xToken, возврат будет следуюшим:
{
    "data": null,
    "error": {
        "message": "Check your permissions",
        "code": "-1",
        "caution": "Something Happened"
    }
}

Поле "data" явным образом содержит null.
Поле "error" содержит объект с следующими полями:
- "message": Поле, которое содержит строку, которую клиетское приложение может отобразить пользователю.
- "code": логический (НЕ HTTP) код возникшей проблемы.
- "caution": Разъяснение для разработчика клиентского приложения.
При этом, если сервер обработал полученный запрос, то HTTP статус будет 200.
Исключение составляет middleware логика, как, например, проверка xToken в HEADER REST запроса. В этом случае, HTTP STATUS будет соответвовать стандартной таблице статусов. Однако, это поведение легко можно изменить внеся нужные коррективы в код middleware.go пакета rest.

## MQTT
----------------
MQTT - легкий протокол для обмена сообщениями между клиентскими приоложениями через внешний брокер. Часто используется  IoT устройствами.
Для подключения к серверу MQTT используются следующие параметры:
* MQTT_HOST - хост или ip адрес MQTT брокера.
* MQTT_PORT - порт - стандартный порт 1883
* MQTT_PROTOCOL= протокол указываемый в строке подключения. Выбор между mqtt:// и ws://. mqtt:// более употребим, поскольку работает на бинарном уровне. ws (Web Socket) использует текстовую сериализацию.
* MQTT_USERNAME - имя пользователя, если он зарегистрирован на сервере.
* MQTT_PASSWORD - пароль пользователя, если он зарегистрирован на сервере.
* MQTT_ROOT - Корневой узел, с которого начинается просмотр. Его следует задать, в случае использования публичных, но не персонализированных брокеров или использование брокера для разных групп esp устройств на одном и том же MQTT сервисе.
* MQTT_CLIENT_ID - параметр, который позволяет отличить разных клиентов друг от друга. В данном случае, сервер выступает клиентом брокера. Если два клиента подключаются с одним ClientID, то произойдет событие отключения. Рекомендуется использование UUID7. Если параметр не будет задан, то имя клиента будет создано автоматически, на основе Unixtime.
* MQTT_KEEP_ALIVE - Проверка на время жизни подключения. Обычно, 60 секунд.
* MQTT_PING_TIMEOUT - Время, которое ждет клиент на свой запрос. Обычно 5-10 секунд.

*Константы*
*	defaultRetained           = false - определяет необходимость сохранения сообщения между сессиями (переподключениями).
*	defaultQOS                = 2     
  - 0 - быстрая доставка, но не гарантированая.
  - 1 - быстрая доставка, но сообщения могут дублироваться.
  - 2 - медленная доставка, но гарантированно будет доставлено тоько одно сообщение.
*	defaultAutoReconnect      = true - автоматическое переподключение, в случае разрыва соединения.
*	defaultShowingMessages    = true - отображение цикла обмена сообщениями в консоли.
*	defaultRemoveAfterReceive = true - указание на удаление полученного сообщения с брокера. (а чтоб меньше отсвечивать).

## Kafka:
-------------------
Kafka - индустриальный протокол логгирование событий микросервисной архитектуры. Является стандартом при использовании Kubernetes.
Kafka не является неотъемлемой частью продукта. Если при запуске сервера он (Франц Кафка), не будет инициирован, то все дальнейшие обращения (отправка сообщений) будут проигнорированы. 

Переменные окружения:
* KAFKA_HOST - хост. По-умолчанию localhost.
* KAFKA_PORT - порт. По-умолчанию 9092.
* KAFKA_ROOT - корневой топик, в который пишутся события о старте сервера.
* KAFKA_ACKS - уровень подтверждения сохранения записи. По-умолчанию All - самый медленный, но надежный режим. Параметр можно не задавать.
* KAFKA_TIMEOUT - таймаут. По-умолчанию 10 секунд.

Топики:
 * actions - События топика action MQTT.
 * logs - важные события сервера.
 * pins - лог изменений значений цифровых и аналоговых пинов зарегистрированных в системе микроконтроллеров.
 * photos - лог получения фотографий от esp32-cam (mqtt типик 'photo').
 * root - события старта сервера и прочая важная информация.

 Запись важных событий в Kafka производится путем вызова domain.Log.Log(<ARGS...>) c переменным количеством аргументов. Переданное таким образом событие предварительно отображается в консоль, а затем отправляется в Kafka,в том случае, если Kafka инициализирован.

## MinIO:
-------------------
MinIO - Хранилище внешних файлов и / или фотоснимков для esp32-cam.
MinIO может отсуствовать для минимальных конфигураций.

Переменные окружения:
* MINIO_ENDPOINT - хост:порт, например "minio-service:9000"
* MINIO_ACCESS_KEY - логин доступа, например "minioadmin"
* MINIO_SECRET_KEY - пароль доступа, например "minioadmin-secret-password"
* MINIO_BUCKET - группа файлов, например "esp32-photos"
