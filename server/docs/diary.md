# Размышления.
# ===============

**Database**
* Вместо устаревшего sqlite3 был использован нативный драйвер modernc.org/sqlite.
* В объект Database было внесено поле, которое указывает имя драйвера, которое использовано в приложении. Это было сделано, чтоб можно было оперативно переключить тип использованной базы данных, и перенаправить поток на использование специфического диалекта.
* НЕОЖИДАННОСТЬ! modernc.org/sqlite не поддерживает миграцию из коммандной строки. 'migrate -help' вообще не имеет драйвера для sqlite. Принято решение делать миграцию на уровене кода. А, поскольку, файлы миграции не могут находится там же, где и исполняемый файл, то они были перенесены внутрь виртуальной файловой системы.
* Семантика SQL разных СУБД отличается. Файлы миграции располагаются в папке database/<СУБД>/schemes.
* В первоначальном варианте Postgres присутствует в виде заглушек.

**Web**
В планы не входило создание административной панели, однако, она была сделана.
* В настоящий момент доступны следующие страницы:
  * - индекстная.
  * - /login
  * - /devices - перечень устройств. Выглядит по-разному, в зависимости от авторизации.
  * - /devices/upload -  форма загрузки .csv файла.
  * - /devices/info - детальная информация об устройстве.
  * - /devices/cfg - страница, на которой можно поменять параметры устройства.
  * - страница с информированием об ошибке.
* Админская панель работает следующим образом: с индексной страницы пользователь может перейти, либо на страницу с сокращенной информацией о полном списке девайсов, либо на страницу авторизации.
* На странице авторизации пользователю предлагают ввести токен. В данном случае, используется X-Token, который изначально устанавливается при старте сервера.
* Если токен введен, то он будет автоматически использоваться на всех веб-страницах. После авторизации, на главной странице можно осуществить деавторизацию. В этом есть необходимость, если для просмотра информации об устройствах использовался "чужой" компьютер.
* Если авторизированный пользователь входит на страницу /devices, то ему доступны следующие возможности:
  * - фильтр списка по начальным символам полей SSDP и MDNS.
  * - сброс фильтра.
  * - выбор устройства для детального изучения.
* Если авторизированный пользователь выбирает устройство среди перечня, то ему открывается страница с детальной информацией. На самом деле, смысл в этом переходе состоит в том, чтоб отобразить поле "last action", которое может содержать довольно увестый JSON. Данный JSON может содержать инструкции, которые микроконтролелер должен будет выполнить при первой возможности. К примеру, новую конфигурацию микроконтроллера. Конкретные действия зависят только от фантазии разработчика прошивки. Цель поля - отобразить последние инструкции, которые были переданы микроконтроллеру.
* Внизу страницы с информацией имеется кнопка удаления устройства с switch боксом для подттверждения действия. Они появляются только в том случае, когда устройство находится в состоянии Timeout. Для активного устройства в этом нет смысла, потому что оно будет автоматически добавлено, если пришлен mqtt уведомление.
* На странице конфигурации, все параметры опциональны. При отправке данных, заменяются только параметры, которые были изменены. 

**Upload**
Загрузку .csv файла можно осуществить как со страницы /devices/upload, так и при помощи REST API: POST /api/v1/devices/upload. В последнем случае, заголовок должен содержать поле xToken с установленным значением. Кроме того, для передачи файла можно использовать утилиту *curl*.

**Зависимости**
Есть большой соблазн сделать так, чтоб объекты моделей сами запрашивали базу данных и выполняли бы действия, в соответствии со внутренней бизнес-логикой. Однако, это либо порождает цикличность ссылок между объектом подключения базы данных, либо делает невозможным использование типа модели в пакете работы с базой данных. В последнем случае, в методы БД приходится передавать "сырые" типы, что противоречит самой концепции моделей. В этой связи, ссылка на БД присуствует только в объекте сетевого подключения, и, некоторая бизнес-логика располагается в обработчике запроса.

**.CSV**
Есть некоторая странность, при работе с табличными приложениями. К примеру, при экспорте из OnlyOffice вначале файла вставляется невидимый символ. Обычные текстовые редакторы и IDE его не отображают, но он становится видимым в объектах REST запросов, и может препятствовать нормальной фильтрации или обновлении данных. Попытка удаления символа в редакторе - не имеет успеха. Самым простым способом является копирование из открытого в блокноте файла, в файл, который был создан самим блокнотом.

**MQTT**
В том случае, если нет возможности развернуть у себя MQTT сервис, можно **временно** использовать публичный тестовый MQTT сервер test.mosquito.org. Следует понимать, что вся информация, отправляемая на *test.mosquito.org* будет публично доступна. Однако, короткое время жизни сообщения, позволяет воспользоваться данной возможностью достаточно безопасно. Разумеется, использование этого сервиса строго *НЕ РЕКОМЕНДУЕМО*, но допустимо - из-за высокой нагруженности публичного сервера, он может не отвечать, и в этом случае, сообщения могут быть потеряны. Чтоб отделить собщения других пользователей от своих собственных, следует подписываться на свой собственный корневой топик, к примеру, сгенерированный UUID7.
Ниже приводятся параметры .env файла, которым могут быть использованы для подключения к публичному брокеру.
MQTT_HOST=test.mosquitto.org
MQTT_PORT=1883
MQTT_PROTOCOL=mqtt://
MQTT_USERNAME=
MQTT_PASSWORD=
MQTT_ROOT=<YOUR_UUID_VER7>
MQTT_CLIENT_ID=<YOUR_UUID_VER7>
MQTT_KEEP_ALIVE=60
MQTT_PING_TIMEOUT=10

*ВАЖНО!* Микроконтроллеры работают на Quality of Service (QoS) 0, а сервер, на QoS 1. Это значит, что сообщения от микроконтроллеров могут теряться в сетевых штормах. В данный момент не предусмотрена настройка на изменение этого параметра через конфигурационный файл. В случае необходимости, данный праметр необходимо править непосредственно в коде. Искать QOS в исходном коде сервера и прошивки микроконтроллера.

**Kafka:**
Кафка применяется для логгирования событий сервера и esp устройства в хранимой, циклически перезаписываемой базе данных. Просмотр можно осуществлять через Kafdrop по адресу localhost:9000 (конечно, если Kafka установлена в Docker локально). *Если нет необходимости использовании Kafka, то соотвествующие методы инициализации Kafka МОЖНО закомментировать в функции main*, а можно просто игнорировать.
Где было возможно, вместо fmt.Println(<ARGS...>) используется domain.Log.Log(<ARGS...>). В обоих случаях метод использует переменное количество аргументов. Если Кафка не инициализирован, то в консоль отобразятся переданные аргументы, а если инициализирован, то это же сообщение будет добавлено в журнал logs Кафки.

**esp32-cam**
Общий механизм: esp32-cam -> mqtt -> esp-server -> storage.
Для управление камерой на странице конфигурации устройства предусмотрено поле 'mode'.
Значение поля соответствует следующим режимам работы камеры:
* 0 - IDLE             *Простой (ничего не делаем)*
* 1 - CONTINUOUS       *Съемка каждые N сек до остановки*
* 2 - BURST_COUNT      *Сделать M снимков каждые N сек*
* 3 - BURST_TIME       *Снимать каждые N сек в течение K секунд*
Название режима, соответвуют константам в прошивке esp32-cam.
Для отображения блока конфигурирование камеры на web старнице, в поле MDNS должна присутствовать подстрока "-cam".
В качестве хранилища снимков, используется *MinIO*
